# Timo bank transfers and Gmail reconciliation

This is a real VND bank-transfer integration, not a sandbox or simulated gateway.
It covers Credit and paid Subscription orders, including daily quota additions.
PayPal/USD and immediate internal activation of free plans are unchanged.

## Trust Boundary

- The receiving bank is Timo by BVBank, VietQR BIN `970454`.
- Each order snapshots its receiving account, name, exact VND amount and unique
  payment code. The QR is generated by `img.vietqr.io`; no bank password is used.
- Original notifications must arrive directly in the configured Gmail account.
  Use a dedicated mailbox with no unrelated recovery mail, OTPs or personal mail.
- Gmail OAuth must have only `https://www.googleapis.com/auth/gmail.readonly`.
  Gmail grants mailbox-wide read access, not access restricted to one sender.
  Use a separate OAuth client/project from public Google Login and Google Drive.
- The worker verifies the original MIME message using DKIM and DNS, not a
  display name, From header alone, screenshot or Authentication-Results header.
  Only `support@timo.vn`, a full-body SHA-256 signature from `timo.vn`, and signed
  From/To/Subject/Message-ID/Content-Type headers are accepted.
- The Vietnamese template must identify the configured account holder, a Spend
  Account increase, amount, Vietnam-local time and exactly one NAP/PRO code.
  Current balance is never used as the transferred amount. Outgoing transfers
  never grant benefits.
- IMPORTANT: the supplied Timo template does not contain a bank account number
  or bank transaction reference. Mailbox + account holder + Spend Account is
  therefore an operator-confirmed, one-to-one binding to the receiving account.
  Do not reuse this mailbox for another receiving bank account. If account-number
  verification against the bank itself is required, use an authenticated bank
  transaction API instead of email notifications.
- The bank-signed Message-ID supplies receipt identity. Immutable receipts and
  atomic order approval prevent double grants, including across multiple emails.
- A mismatch, missing code, duplicate payment for an already approved order,
  unavailable voucher/purchase limit or unsupported template goes to admin
  reconciliation. Never silently credit an underpayment or overpayment.

## Configure Production

Enable transaction emails in the Timo app and confirm the exact recipient,
account holder and receiving account. Authorize the Gmail account using an
OAuth client in production publishing status, not Testing. External/Testing
refresh tokens with Gmail scopes expire after seven days. An integration used
only by its owner can qualify for Google's personal-use verification exception;
do not request mailbox access from website customers.

Store the following only in `/etc/3dipl/production/backend.env`:

```dotenv
VND_PAYMENT_PROVIDER=timo
TIMO_ENABLED=true
TIMO_MAIL_WORKER_ENABLED=true
TIMO_ACCOUNT_NO=<receiving account number>
TIMO_ACCOUNT_NAME=<exact account holder name from the bank>
TIMO_GMAIL_ADDRESS=<Gmail receiving original Timo notices>
TIMO_GMAIL_CLIENT_ID=<dedicated Google OAuth client ID>
TIMO_GMAIL_CLIENT_SECRET=<dedicated Google OAuth client secret>
TIMO_GMAIL_REFRESH_TOKEN=<refresh token with gmail.readonly>
TIMO_MAIL_START_AT=<ISO UTC timestamp for the activation, for example 2026-10-18T00:00:00.000Z>
```

Choose the actual activation timestamp; do not paste the example timestamp
blindly. Never rotate the mailbox/account binding while orders await payment.
The Gmail connection in Codex is not a credential for the VPS. Tokens must be
granted explicitly to the backend OAuth client and never pasted into chat/Git.

To obtain a refresh token with Google's OAuth Playground, register its exact
redirect URI `https://developers.google.com/oauthplayground`, select **Use your
own OAuth credentials**, **Offline**, and the Gmail read-only scope. Authorize
the intended mailbox and exchange the authorization code. Do not use the
Playground's shared/default credentials, whose grants are short-lived.

Build the new backend before running the new check script:

```bash
cd /opt/3dipl/app
git pull --ff-only origin main
sudo docker compose -f compose.production.yml build backend frontend </dev/null
sudo docker compose -f compose.production.yml run --rm --no-deps -T \
  -e NODE_ENV=production backend npm run env:check </dev/null
sudo docker compose -f compose.production.yml run --rm --no-deps -T \
  backend npm run timo:check </dev/null
sudo docker compose -f compose.production.yml run --rm --no-deps -T \
  backend npm run timo:check -- --verify-latest </dev/null
```

`timo:check` is read-only: no database connection, approval, email modification
or bank transfer. It proves the OAuth token belongs to the expected mailbox.
It does not by itself prove bank notices pass signature verification.
`--verify-latest` reads and verifies the latest original Timo email, without
approving it. A personal transfer without an order code can prove mailbox and
bank-email authenticity but can never pay a website order. The local
`--eml <path>` option likewise verifies an original email without approving it.
Check DKIM/DNS access on the actual VPS; do not fall back to trusting email
headers when DNS is unavailable.

Once configuration and the receiving account are verified, recreate services:

```bash
sudo docker compose -f compose.production.yml up -d \
  --no-deps --force-recreate --wait --wait-timeout 180 backend frontend </dev/null
curl -fsS http://127.0.0.1:5000/ready
```

Keep old SePay secrets until old SePay orders finish; IPN endpoints remain
available for those orders even when `SEPAY_ENABLED=false` stops new checkouts.
The bank details in each already-created order remain unchanged by later env
edits. There is no cross-provider approval: SePay/VietQR webhooks cannot approve
a Timo or PayPal order.

## Operations

- VI checkouts use the advertised VND provider. EN uses PayPal as before.
- Users remain on the site, see QR/details, and poll their owned order every
  five seconds. The URL retains the order identity across refresh. Success uses
  existing account events, immediate balance refresh and Telegram notifications.
- The worker polls every 30 seconds with a persistent lease, paginated scan
  checkpoint, overlap window and durable pending events in Atlas Core.
- Restart does not lose verified payments. Benefit grants and receipts use the
  same Atlas transaction services as existing payments. No raw emails, tokens,
  full bank balances or attachments are stored in the database or logs.
- Admin > General > Credit / Subscription transactions includes the mailbox
  health, latest events, review reasons, reconcile-now and reverify controls.
  Admin auth, 2FA, CSRF, write rate limits and audit logging apply. Retry always
  re-reads and re-verifies the original bank email; it does not bypass a check.
- Unmatched/late/failed payments are retained and alerted for manual review.
  Do not tell a user to pay again solely because email delivery is delayed.
- A 30-minute order deadline releases unused voucher/purchase reservations.
  A genuine late payment is still reconciled; if benefits can no longer be
  granted safely it requires admin review rather than disappearing.
- If Gmail authorization is revoked, reauthorize the dedicated mailbox, update
  its refresh token and recreate backend. Do not replace the Drive token.

## Rollback

Set `VND_PAYMENT_PROVIDER=sepay`, `TIMO_ENABLED=false` and restore SePay new-order
configuration to switch new VND checkouts back. Keep
`TIMO_MAIL_WORKER_ENABLED=true`, the bank binding and Gmail credentials until all
outstanding Timo payments have been reconciled. Keep the current backend during
this drain; never delete events, receipts or subscription periods to roll back.

## Validation Handoff

- Local `npm run check`: 592 tests, lint and frontend release build passed.
- Mock browser QR checkout/recovery/settlement: VI/EN, light/dark, desktop/mobile
  (eight combinations) passed. Whole-site smoke passed on both viewports.
- Production dependency audit reported no vulnerabilities at implementation time.
- Automated payment tests use fixtures only; no real money or production database
  is touched. The supplied personal bank email is not tracked in Git.
- Live Gmail OAuth and cryptographic verification of an original bank notice on
  the actual VPS remain deployment prerequisites. Local DNS could not confirm
  the supplied original signature; an Authentication-Results header is not proof.
